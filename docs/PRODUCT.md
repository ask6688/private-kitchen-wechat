# 私人厨房的产品逻辑

## 为什么做

朋友或情侣一起做饭时，菜谱、想吃的菜、当天安排和做完后的照片常常分散在聊天、收藏和相册里。私人厨房把这些内容收进同一空间，让“想吃什么 → 这次做什么 → 这顿饭怎么样”形成可回看的闭环。

产品为两位成员服务：共同维护内容，自己挑选菜品，提交后合进同一份饭单。它没有支付、配送或公开社区。

## 五种内容

| 内容 | 用途 | 和其他内容的关系 |
| --- | --- | --- |
| 菜单 | 反复做、想继续维护的长期菜品 | 保存分类、标签、外部菜谱、食材和步骤；详情可回看历次下厨 |
| 心愿 | 下次想吃或想试的菜 | 共用菜品录入；实现后关联菜品进入菜单 |
| 饭单 | 安排本次开饭 | 菜单与心愿均可选择，保留名称与分类快照 |
| 做一道菜 | 记录一次下厨 | 选已有菜，或记录新菜并选择是否收进菜单 |
| 一起吃饭 | 记录一顿饭 | 饭单完成或直接补录，保存单菜/整餐心得、照片及完整 Menu |

## 典型流程

1. 创建厨房并邀请伙伴，双方共同维护分类、菜品和心愿
2. 从菜单和心愿挑菜，本机选择暂不写入云端
3. 一次提交选择，合并到厨房当前饭单，填写日期和人数并确认
4. 开饭后完成饭单，留下单菜或整餐照片与心得
5. 从最近记录、一起吃饭列表进入同一 Menu 详情，再查看完整纪念图

也可以直接记录一次下厨或一顿已吃过的饭，不要求先创建计划。

## 需要守住的规则

- **只有一个当前饭单**：两人的选择合并到同一份安排。确认后仍能明确撤回修改；重开历史饭单前需要处理已有当前饭单。
- **历史保留当时内容**：菜品改名、分类改名或归档不会随意改写已保存的历史快照；兼容字段缺失的旧数据。
- **照片按场景归属**：菜品封面、单菜记录和整餐相册各自保存引用，删一条记录不会连带删除其他内容。
- **制作次数有依据**：由实际制作记录维护；编辑、重复点击和网络重试不能虚增次数。
- **成功反馈跟随真实结果**：保存失败或冲突保留输入；删除前确认，失败时允许核对与重试。
- **双人共同维护，管理边界明确**：两人可编辑内容；邀请、移除和移交负责人由负责人操作。退出或被移除后失去云端访问资格。
- **导出可理解**：JSON 包含菜谱、记录、历史数据和照片引用清单；照片原图需要另行备份。

## 页面组织

四个一级入口为菜单、心愿、记录、我们。饭单由菜单的当前饭单入口或选菜提交进入。二级选择页复用一级页逻辑，保留来源页面和返回关系。

当前实现范围、技术可靠性和仍需人工验证的部分分别见 [架构说明](ARCHITECTURE.md) 与 [验证清单](ACCEPTANCE.md)。
